# Node1 Ord 索引与停止优化依据（2026-09-28）

本记录是改动前的只读实测基线，不是新策略已完成线上性能验收的结论。使用现有数据诊断，未清库、调参或重启服务；
停止与升级由运维人员发起。对外操作说明见 [Ord 手册](../handbook/services/ord.md)。

## 改动前观测

- 原 r33 服务在 12:16:47 UTC 收到停止信号，Ord 输出 graceful shutdown。
- 12:21:33 至 12:24:02，Ord 进程 `write_bytes` 增加 859,783,168 字节（约 820 MiB），数据文件仍被修改。
- 12:26:47，Docker 发出 SIGKILL，退出码 137。实际 `StopTimeout=600`；此前无 OOM 记录。
- 原管理脚本在 `child.wait()` 前写 `STOPPED`，覆盖最后高度，无法从该文件还原停止进度。
- 运维升级到 r40 后，12:33:50 HTTP 已监听；12:40:37 至 12:43:15，Ord `/blockcount=590000`，已提交高度 589999。
  Core 历史与 txindex 均已覆盖前台（采样高度 968996–968997）。
- 12:40:37 至 12:41:48，Ord 写计数从 3,890,929,664 增加至 4,808,077,312（约 875 MiB）；已提交高度没有变化。
- 数据文件约 32 GiB，地址索引已启用；Ord 容器 4 GiB、数据库缓存 1 GiB、CPU 上限 2 核。
  主机 MemTotal=65,720,652 KiB，可用约 57 GiB。采样无 CPU 节流、无 OOM。
- 15 秒数据盘样本：busy 约 100%，读约 2,903 IOPS / 14.0 MiB/s，写约 238 IOPS / 1.1 MiB/s。
  Ord I/O PSI 明显；这些进程和设备计数口径不同，不能直接用作逻辑数据库增量或加速比。

## 推论与改动边界

数据库已打开且持续工作；高度停留不能解释为持续 loading。高度是已提交视图，5,000 块批次内部工作缺少可见性。
小缓存与固定容器额度值得改进，现场有明确 I/O 瓶颈，但本次没有受控的配置对照实验，不能断言唯一根因或承诺加速倍数。

新自动策略使用显式 `USDB_ORD_MEMORY_CAP` 标识；旧环境未携带该字段时仍按旧额度计算。
setup / 显式重算时按约四分之一内存分配 Ord、默认上限 16 GiB、缓存占一半，纳入所有阶段整机预算。
以本次 MemTotal 计算为 Ord 约 15.67 GiB、缓存约 7.83 GiB；不依据瞬时空闲内存不断重启服务调参。

新观测读取固定版本 Ord 的 INFO 里程碑，不修改 Ord 索引算法、索引 schema、默认提交间隔或既有数据库。
事件文件约 6 MiB 轮转；进度区分处理高度、提交目标、已提交高度及进程读写。
`down` 先用 Docker `stop --timeout -1` 等 Ord，保留重启策略的正常停止语义；中断只结束等待客户端。
直接 Docker 操作和宿主机关机仍由各自的 grace period 决定。

## 发布后验收

更新 node kit 与 usdb-services 镜像，停机后显式重算 auto 策略，保留现有索引。核对实际 cgroup 额度和缓存启动记录，
观察至少两个批次的处理高度、提交耗时、I/O 与核心服务健康。计划停机时确认 STOPPING 持续更新、进程退出后才 STOPPED，
Docker 退出码 0，事件文件在容器移除后仍存在。前后位于不同历史高度的样本不能直接推导准确加速比。

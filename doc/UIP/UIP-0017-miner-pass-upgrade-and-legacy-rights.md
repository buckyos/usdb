# 摘要

本文定义 MinerPass 后续升级对存量 pass 的默认处理原则，以及例外处置必须遵循的提案要求。版本与高度选择沿用 [UIP-0008](./UIP-0008-protocol-versioning-and-activation-matrix.md)，不新增另一套激活机制。

默认策略是：收紧新 mint 准入条件不追溯作废旧的合法 mint；存量 pass 保留其状态，后续增长、操作和继承按事件发生高度的已激活规则执行。改变某类存量 pass 的后续权益必须由独立升级 UIP 明确规定。

本文为 Draft，不表示委员会已审议通过、参考实现已支持跨版本迁移，或任何网络已激活新规则。本次仅整理协议草案，不更改 JSON、registry、genesis、数据库或在线节点。

# 动机

“某种 mint 从高度 H 起不再被接受”与“该类存量 pass 从 H 起失去权益”是不同的协议变更。若不明确区分，节点可能在软件更新、历史回放或继承时产生不同结果。格式升级也不应隐式取消既有 pass 的权益。

本规范适用于需要保留历史的网络。已明确采用全新数据集的开发网重置仍遵循 UIP-0016，不借本规范恢复已舍弃的开发期状态。

# 术语

- pass 状态、owner、`prev` 沿用 UIP-0001 / UIP-0002；raw energy 与继承折损沿用 UIP-0003；协作关系沿用 UIP-0004。
- **H**：具体升级在指定 BTC source / rules scope 中的 BTC 激活高度。
- **存量 pass**：reveal 高度小于 H、已按当时规则接纳且仍存在于规范状态中的 pass。存量不等于 Active，仍须区分 Dormant 和终态。
- **默认保留**：不因新 mint 准入规则而重新判定旧 mint；不保证旧公式、操作权限或收益永久不变。
- **例外处置**：具体升级显式改变某类存量 pass 的后续资格、状态、能量或继承权利。

# 规范

## 版本与事件高度

1. JSON `v` 选择载荷格式，状态机与公式由目标网络的 registry 和事件 BTC 高度选择；程序发布号、安装时间和服务重启不得决定协议行为。
2. mint 采用 reveal 所在规范 BTC 区块的高度，不采用 commit 高度。commit 在 H 前、reveal 在 H 或之后的操作必须满足新准入规则。
3. schema 升级提案必须列明各阶段允许的新 mint JSON 版本及解析语义。引入 schema v2 不自动意味着继续接收或禁止 schema v1 的新 mint。
4. 历史 mint、状态变更和经济结果必须按各自高度重放；新程序必须保留必要的旧执行逻辑。不支持该高度的版本时停止执行并报告错误，不得回退到另一版本，也不得将数据不可用记为 pass Invalid。
5. BTC-side 激活高度与 USDB chain checkpoint 是不同锚点；具体配置、registry revision、历史保留和双方校验按 UIP-0008 执行。

## 多次升级与每张 pass 的适用规则

同一 BTC source / rules scope 的历史可以分为 `[origin, H1)`、`[H1, H2)`、`[H2, H3)` 等区间。这里的区间由相关已激活版本族的边界共同划分；一次升级可以只改变 energy 公式而保持 schema、状态机及其他公式不变，区间编号不是新的统一协议版本。

规则关联分为两层：

| 信息 | 作用 |
| --- | --- |
| pass 的铸造事实与历史状态 | reveal 高度、JSON 版本、已接纳的字段和规范状态历史，用来解释原始 mint 及后续事件。 |
| 网络的按高度规则时间表 | 在指定 registry revision/source/scope 下解析当前事件高度的完整 active version set，处理该 pass 在此时的操作和经济结果。 |

一张在第一区间铸造、跨越后续多个区间的 pass，其 mint 合法性仍按第一区间解释；后续行为依次按所在区间的规则处理。旧证保留是当前规则对历史资格的承认，不是把该 pass 的未来行为永久固定到出生时的规则。

例如，P 在 H1 前已合法 Active，余额不变、后续没有转移或例外处置，且各阶段能量表示兼容：

| 处理区间 | 规则和累计状态 |
| --- | --- |
| P 铸造后至 H1 前 | 按 R1 结算已发生的增长，得到该区间结束时的状态 S1。 |
| H1 至 H2 前 | 在 S1 基础上按 R2 结算该区间，得到 S2；不把 R2 应用于 H1 前的时间。 |
| H2 及之后 | 在 S2 基础上按 R3 继续结算；不重新检查 P 是否符合 R3 对新 mint 的准入条件。 |

表中 R1/R2/R3 表示区间规则集合，S1/S2 包括能量以及后续计算所需的状态，不只是一个能量数值。实际块端点和 mint 当块是否增长沿用对应 UIP 的定义；本例不重新定义 UIP-0003 的计数方式。

如果某次提案需要区别对待不同铸造区间、JSON 版本或继承来源的 pass，必须在该高度的统一规则中明确对象判定和结果；涉及存量权益减少时仍须遵循例外提案要求。pass 持有人或索引器不得自行选择对其有利的历史规则。

## 跨多个区间的结算与恢复

从已结算高度处理到目标高度时，必须按规范顺序经过全部相关激活边界、余额变化和 pass 状态事件，即使期间没有发生该 pass 自身的交易。每段以之前的完整状态作为输入，输出下一段需要的状态。

- 若单位、状态表示或其他必要字段变化，必须先按对应升级规定的时序执行转换，再继续该阶段计算；转换无变化时可以是显式声明的恒等转换。
- 不得仅将“铸造版本”和“当前版本”做一次比较后跳过中间升级。逐段迁移路径中的每一步都必须已定义；直接跳转或合并计算只有在能够证明与规范分段结果完全一致时才允许。
- 只有在单位兼容、没有转换或扣减且公式允许时，才能将各段增长直接相加。涉及舍入、饱和、惩罚或单位年龄等状态时，必须保持规范计算顺序，不能把通用处理简化为各段数值求和。
- Dormant / 终态的零增长不代表可以跳过该状态适用的边界处理；是否改变其状态表示或继承资格由具体升级规定。
- 边界处置必须相对于该区块事件有唯一顺序，并在同一规范链历史中生效一次；重启不能重复扣减，跨边界 reorg 必须撤回对应转换与处置。

实现可以共用一份网络规则时间表，不要求为每张 pass 复制区间列表或每块写入一条记录。可从既有共识历史重建的规则 ID / 区间标记可以作为缓存；若新增字段无法派生，则须另行定义其版本、commitment 和快照语义。物理上惰性结算与逐块处理必须得到相同的状态、查询和承诺结果，不能因是否访问过某张 pass 而不同。

快照与结算记录必须足以确定恢复点已处理到哪个规范高度、使用的状态表示及历史上下文。恢复后只处理尚未执行的区间；历史查询仍按查询高度解释。跨版本 `prev` 应消费经过必要结算和已定义转换后的规范状态，不能直接拿旧快照中的裸能量交给最新公式，也不能从最初 JSON 版本推定当前能量的表示版本。

## 默认存量处理

具体升级 UIP 未提出经评审的例外处置时，必须采用下表，并明确声明这一选择：

| 对象或事件 | 默认要求 |
| --- | --- |
| H 前合法的 mint | 保留历史合法性，不使用新 mint 条件追溯判为 Invalid。 |
| H 前已有 Active pass | 延续其状态；继续按各高度适用的状态机、余额与公式参与能量增长及资格判断。 |
| H 前已有 Dormant pass | 保留状态及已结算能量；不因升级自动恢复增长或激活。 |
| Consumed / Burned / Invalid | 不因升级恢复权益；不能作为可消费的 `prev`。 |
| H 及之后的新 mint / remint | 无论是否引用旧 pass，都必须通过新 schema、来源、目标地址及 `prev` 校验。 |
| 升级前已经确定的历史结果 | 按历史上下文查询、重放；不得因部署新版软件重新解释。 |

保留旧 pass 不豁免后续规则：转移、烧毁、余额变化、协作资格和新 mint 对旧 pass 的消费仍按各自事件高度执行。已确认的 USDB chain 奖励不因旧 pass 的未来资格变化被回溯重算。

若改变 energy 公式，必须规定跨 H 的结算分段、区块边界、单位、舍入和溢出处理。禁止将 H 后的新公式直接应用到整个历史累计区间；不得将 pass 的未来增长永久锁定为其 mint 时的公式。

## 跨版本继承

1. 在新 mint 执行时读取 `prev` 的规范 owner 和状态，验证来源及消费资格；不重新按新 mint 准入条件审判旧 mint。
2. 新 mint 必须全部校验成功后才能结算、休眠或消费旧 pass；失败不得部分消耗旧权益。继承成功后的状态与防重复消费沿用对应已激活状态机。
3. 每次升级必须显式声明旧能量、字段和状态是否兼容。兼容时按新操作高度适用的继承规则和折损处理，不意味着全额无损转移；不兼容时必须定义确定性转换函数及失败条件。
4. 未提供兼容声明或转换函数的组合，禁止跨版本继承。默认保留旧证不能替代这项兼容证明。
5. 新 pass 后续行为按后续事件高度的规则执行。Leader/collab 绑定是否延续按 UIP-0004 和具体升级提案规定，不能暗含跨地址或跨 pass 自动跟随。

## 例外处置必须另提 UIP

若需要冻结、停止增长、撤销挖矿/协作资格、禁止继承或减少存量能量，必须先提出独立的 Standards Track UIP，明确它偏离本规范默认策略的部分。可以在提案阶段进行隔离原型验证；目标网络启用前必须完成规定评审、实现、验收及激活配置冻结。安全紧急性不构成隐式修改共识的授权。

例外提案至少必须规定：

| 项目 | 必须说明的内容 |
| --- | --- |
| 原因和范围 | 风险依据、替代方案、受影响的网络/source/scope，以及为什么默认保留不足以解决问题。 |
| 确定性对象集合 | 按哪一高度的规范状态、哪些字段或承诺数据识别对象；不能依赖运行时远程名单或节点本地判断。 |
| 激活边界 | BTC 高度 H、必要的 USDB checkpoint，以及处置相对于 H 块内交易和能量结算的准确顺序。 |
| 权益矩阵 | Active/Dormant/终态分别如何处理；raw/effective energy、挖矿、协作、继承、收益绑定的变化。停止增长不等于禁止挖矿，也不等于禁止继承。 |
| 历史与迁移 | 保留 H 前历史；明确 H 后是否保留、冻结、转换或扣减累计值，状态如何表示并进入 commitment、RPC 与快照。 |
| 防绕过 | 明确是否覆盖已继承的后代 pass、同址 remint、跨地址继承、转移和协作绑定，以及这些路径如何确定性识别。 |
| 双链衔接 | 如要求某 USDB 高度起停止收益，必须规定是否仍允许引用 H 前的 BTC anchor；仅设置 BTC H 不等于所有后续 USDB 区块立即停止旧资格。 |
| 恢复与运维 | 跨 H reorg、崩溃重启、历史重放、旧节点行为和数据升级路径，以及对持有人的操作说明。 |

例外不能把 H 前按旧规则合法的 mint 改写成“从未合法”，也不能追溯改变已确认的历史收益。H 后的处置必须作为明确的新状态转移或资格规则执行；其编码、版本及承诺方式由该例外 UIP 定义。本文不预设一个管理员作废接口、任意名单或自动批量 Invalid 机制。

# 激活与版本影响

本文不分配具体升级版本或高度，也不增加 Active registry record。各次升级须提供如下完整信息：

- BTC source、rules scope、旧/新版本族和 registry revision、精确 BTC H。
- 适用 USDB 网络及 chain ID、必要的完整 checkpoint 与 registry binding。
- 采用默认存量策略的声明，或独立例外 UIP 的引用。
- schema 接受集合、跨版本继承兼容声明或转换方式。
- 实现、测试证据、部署与数据兼容方案；没有在线数据库迁移能力时不得宣称原目录直接升级。

提案按 UIP-0000 的 Draft / Review / Last Call / Final 流程推进。委员会/协议评审认可、代码合并、发布和网络激活必须分别记录；即使提案为 Final，也只有目标网络的明确激活配置决定何时执行。其他网络不得自动跟随。

# 向后兼容与参考实现

当前实现仅支持 JSON schema v1 + 状态机 v2，开发网采用重置，未实现本草案描述的通用跨版本迁移或例外处置。UIP-0016 的现有开发网边界保持不变。registry/高度查询框架和 nightly 激活测试通过，不代表所有未来 pass 升级语义已经实现。

未来落地需要同时覆盖 parser/state-machine 分派、按高度能量结算、继承兼容、历史查询、commit/快照/reorg，以及 USDB validator 的规则绑定。新增具体业务语义由相应定义 UIP 或独立升级 UIP 承担，不通过修改服务版本常量隐式实现。

当前源码缺口、分批实施顺序及 fast/nightly/weekly 测试矩阵见[实施与测试计划](../usdb-indexer/miner-pass-upgrade-implementation-plan.md)。计划第 7 节记录已完成批次与本地验证；其余设计项不能视为已实现或已激活。

# 安全性考虑

默认保留可能延续旧规则下已形成的不当权益；因此它是升级默认策略，不是对已知漏洞权益的永久保证。例外处置必须评审误伤、继承绕过和双链 anchor 滞后。规则缺失或不支持时应停止处理，不能以可用性为由选择不一致结果。

# 测试要求

每次具体升级至少提供以下可复现向量；不适用项须说明原因，测试不得只验证 registry 字符串变化：

| 场景 | 验证内容 |
| --- | --- |
| H-1 / H / H+1 mint | 同类 payload 在边界两侧的准入结果；覆盖跨 H 的 commit/reveal。 |
| schema 接受集合 | 旧/新 JSON 版本的允许与拒绝；历史 parser 回放一致。 |
| 存量各状态 | Active、Dormant 和终态的权益矩阵，不因升级隐式激活或作废。 |
| 能量跨界 | 升级前累计值、升级后增长/惩罚、单位/舍入及历史查询精确一致。 |
| 连续多次升级 | 同一 pass 跨至少三个区间，覆盖不同铸造批次、只升级部分版本族、非恒等转换及跨多阶段继承；不以最新规则覆盖历史。 |
| 长期无操作 | 多个激活边界间无 pass 交易，逐块执行、惰性结算和跨区间快照恢复结果一致，转换不漏做或重复。 |
| 跨版本 prev | 兼容/转换、折损、来源及 owner 校验、重复消费、失败原子性、同址与跨地址。 |
| 协作和 Leader | 存量绑定、重新绑定及受影响 pass 对聚合/收益的影响。 |
| 恢复与重放 | H 前后 reorg、重启、快照恢复、从 origin 重建与持续运行结果一致。 |
| 不支持的节点 | 在所需规则生效处明确拒绝执行，不回退、不写入部分状态。 |
| 例外处置 | 对象判定、块内顺序、防绕过、旧 BTC anchor 和 USDB 收益截止语义。 |

# 待定问题

当前没有具体 v3/schema v2 升级或存量撤销对象需要激活。具体版本、网络高度、转换函数和例外权益矩阵由将来的升级提案决定，不在本草案中预先授权。

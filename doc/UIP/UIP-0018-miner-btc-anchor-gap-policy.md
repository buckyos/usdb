# Miner BTC anchor gap 推荐策略

状态：默认 gap=2 的本地策略方向已确认，项目组讨论见 [USDB #52](https://github.com/buckyos/usdb/issues/52)。
本文按 2026-10-14 的讨论收敛，并吸收 [项目组评审意见](https://github.com/buckyos/usdb/issues/52#issuecomment-6139593744)。
gap 尚未实现；本文不改变当前出块策略或网络共识参数。

本文是独立的 Informational UIP，用稳定编号承载推荐策略、参考实现计划、观测和验收，
供跨客户端讨论与引用。Draft 状态不表示委员会已审议通过或功能已发布。
`Activation: None` 表示本地策略无需共识激活高度，也不绑定网络身份。

共识约束以 [UIP-0007](./UIP-0007-usdb-consensus-profile-selector.md) 为准。本文对选高算法、
配置和工具的要求适用于采纳此推荐策略的实现；其他客户端可以采用不同的合法选高策略，
validator 不检查其是否遵循本文算法。改变矿工选择的合法输入可能影响出块结果，但不改变
相同链上上下文和 selector 的验证或经济计算结果。若以后修改合法 anchor 范围、复用规则或
权益计算，须另走 Standards Track 提案及相应版本、激活流程，不能通过修改本文隐式生效。

前置工作已完成本地验收：指定已提交高度查询、Go 延迟验证与自动重试，以及三节点独立
BH/indexer、多矿工恢复矩阵。测试实现见 Go `4c1c18817`，验收记录见 USDB `0bdbc84`。
这些测试证明等待与恢复路径可运行，尚未证明 gap=2 在公网的性能收益。

## 1. 建议与边界

增加可配置的本地矿工选高策略，默认 `gap=2`。矿工可以显式覆盖为其他合法非负值，
包括设为 `0` 恢复最新高度策略，但常规运行不推荐调整。gap 不强绑定网络参数；
其单位是 **BTC block**，不是 USDB block，也不是固定时间。

- BH 的 `stable_lag_blocks=10` 保持不变；gap 在 indexer 最新完整提交高度上计算，不再从
  Bitcoin tip 重复减去 10。正常追平时，所选高度约为本机 BTC tip 减 12；索引落后时会更旧。
- gap 是优先目标，不是必须满足的距离。父 anchor、复用上限、索引起点可以使实际 gap 小于 2。
- validator 仍只按区块携带的 selector 和父块校验，不检查生产者的 gap，不要求自己也满足 gap。
- 不新增 header 字段、不变更铭文 schema、公式、registry、genesis、chain/network ID，
  不要求重索引、网络重置或设置共识激活高度。已有合规 validator 可验证这种历史 selector。
- 保留延迟验证与自动重试。gap 不能替代它们，也不是 BTC finality 或全网同步程度的证明。

预期收益是：为其他节点同步同一 BTC 状态留出余量，减少正常跨节点延迟导致的暂缓验块。
这有望改善传播和出块利用率，不改变共识安全规则，也不保证提高吞吐或消除竞争分叉。

### 默认 2 的量化依据与适用前提

需要缓冲的是同一 BTC 状态在节点间的可用时间差。设某状态 `H` 在快节点可用后，
validator 还需 `w` 秒才可查询同一身份。先作一个用于解释默认值的简化模型：

- 节点持续追平，逐高度及时提交；不存在批量补历史、父 anchor 让步或故障。
- BTC 块间隔相互独立，按均值 600 秒的指数分布近似；忽略索引处理和传播时差的波动。
- `w` 暂视为固定值；理想缓冲 `S_G` 为随后 `G` 个 BTC 块间隔之和。

`S_1` 是指数分布，`S_2` 是 Erlang 分布，而不是另一个指数分布。对 `w>=0`：

```text
Pr(S_1 < w) = 1 - exp(-w / 600)
Pr(S_2 < w) = 1 - exp(-w / 600) * (1 + w / 600)
```

| 节点可用时间差 `w` | gap=1 缓冲不足概率 | gap=2 缓冲不足概率 |
| --- | ---: | ---: |
| 10 秒 | 1.65% | 0.014% |
| 30 秒 | 4.88% | 0.121% |
| 60 秒 | 9.52% | 0.468% |
| 120 秒 | 18.13% | 1.752% |

该模型支持先采用默认 2：第二个间隔进一步缓冲 BTC 短间隔连续到来的情形。代价是在这些
假设下相对 gap=0 平均额外等待约 1200 秒，而非固定 20 分钟。模型中的 600 秒取自
[Bitcoin 目标出块间隔](https://github.com/bitcoin/bitcoin/blob/master/src/kernel/chainparams.cpp)，
不表示实测块间隔或节点处理时间始终满足这些分布假设。

表格不是实测区块暂缓率、孤块率或收益损失率。真实引用还受到 USDB 封块时间、区块传播、
索引批处理、延迟相关性和混合 gap 矿工的影响；批量追到 `H+2` 不保证已留出两个正常 BTC
间隔的处理时间。后续按第 5 节采集节点可用时间差和实际等待，验证模型适用程度，
保留默认值调优的证据。默认 2 是本轮初始策略决定，不把理论表格当作已完成的公网验收。

## 2. 选高规则

每次组块固定父块及以下输入：

| 输入 | 含义 |
| --- | --- |
| `L` | indexer 成功返回的最新完整、可查询的已提交高度；不能用 BH 目标或 Bitcoin tip 代替 |
| `G` | 本地配置 gap，建议默认 2 |
| `F` | 已核对的历史查询起点；当前实现对应 `genesis_block_height` / chain 的 `btcIndexOriginHeight` |
| `P, A` | 父 selector 的 BTC height 与 anchor age；首个 selector 没有父 anchor |
| `M` | **待挖 USDB 子块** activation checkpoint 指定的最大 anchor age |

配置 gap 指本地偏好 `G`；实际 gap 指本次组块观察到的 `L-H`，其中 `H` 为最终所选高度。
实际 gap 可以因下述约束而小于配置值；两者均不是链上 payload 字段。

在现有 anchor policy v1 下：

1. `L < F`，或者父 anchor 存在且 `P > L`：等待可验证状态，不向更早高度寻找替代。
2. 先选 `T = max(F, saturating_sub(L, G))`，防止起点附近减法下溢。
3. 有父 anchor 时，选 `H = max(T, P)`；没有父 anchor 时，选 `H = T`。
4. 若 `H == P` 且复用会使 `A+1 > M`（包括计数溢出）：
   - `L > P` 时选 `H = P+1`，让步于 gap，推进到最邻近的新 BTC 高度；
   - `L == P` 时等待新状态，不能继续复用，也不能构造超限块。
5. 精确查询 `H` 的完整历史身份与 candidate；仍调用现有
   `ExpectedBTCAnchorAgeBlocks` 验证完整 transition，不能只凭选高算术放行。
   同高必须保持父块的 `snapshot_id/system_state_id`；前进时 age 为 0。

第 4 步的 `P+1` 只在 `L>P` 时计算，且不超过 `L`。这一步只解决 age 上限，
不是根据 pass 是否有利逐个探测高度。未来出现新 anchor policy 时，必须显式分派，
不能直接套用 v1 的算术。`M=0` 或未知 policy 仍为配置/版本错误。

假定 `G=2`、`F<=98`：

| `L` | 父高度 `P` | 父 age | 选择结果 |
| --- | --- | --- | --- |
| 100 | 无或 97 | 未耗尽 | 98，正常 gap |
| 100 | 99 | `A<M` | 99，受父 anchor 限制，实际 gap=1 |
| 100 | 99 | `A=M` | 100，推进 anchor，实际 gap=0 |
| 100 | 100 | `A=M` | 等待新 BTC 状态 |
| 99 | 100 | 任意 | 等待本地补齐父 anchor，不能退到 97 |

`A=M-1` 时仍允许最后一次同高复用，子 age 恰为 `M`。首次引用 age=0，
所以不能把 `M` 误当作包含首次引用在内的总块数。

当前没有动态 pruning floor，不新增自动搜索“任意可查询高度”的逻辑。起点以上若历史
缺失、裁剪、身份不符或服务处于恢复屏障，保留明确错误和既有重试/运维分类，不能静默改用
current head。若未来支持裁剪，再明确 floor 的 RPC 契约及与验证历史保留责任的关系。

## 3. 历史状态必须贯穿组块

目前 Go `PayloadBuilder.BuildCurrentPayload` 用 `get_system_state_info` 的当前高度构造
context，再调用 `resolve_miner_candidate`。Rust 已有 `get_state_ref_at_height` 和带 context
的历史 candidate 查询；不需要为 gap 新造一套 indexer 状态或能量计算。

建议流程：

1. 读取当前已提交 state，取得 `L`，保留服务 scope、registry 兼容性及安全检查。
2. 按第 2 节仅由高度、父块和配置确定 `H`。
3. 通过 `get_state_ref_at_height(H, context)` 取得该高度的精确历史身份。
   context 绑定当前 USDB checkpoint 允许的 BTC registry；如果复用父高度，还必须绑定父
   snapshot/system ID。检查响应的各高度和身份一致，不能把 `L` 的 ID 搬到 `H`。
4. 使用这个身份调用 `resolve_miner_candidate(usdb_main, H, context)`；校验返回的
   external state、selection rule、pass 和收益地址，构造唯一 selector。
5. 所有 BTC 侧 pass 状态、能量、协作贡献、aggregate 都来自 `H`；USDB 难度、奖励等
   chain policy 仍按待挖 **USDB block number** 激活，再应用到该 historical profile。

BTC activation 按 `H` 解析，不能直接使用 `L` 的 active version set；USDB chain activation
不能因 gap 延后。registry 历史一致性检查仍须保留，不能利用旧高度绕过未知版本或冲突。
两次 RPC 间正常前进不要求 `L` 始终不变；identity mismatch、恢复屏障等仍使本次组块失败，
由已有机制重新读取状态并重试，不能拼接不同时刻的身份和 profile。

所选 `H` 没有本矿工的有效 candidate 时，等待后续状态或显式调整本地配置；不因收益、
能量、旧证仍有效等原因向前后搜索其它高度。同一个 `H` 内仍沿用当前确定的 candidate 排序。
gap=0 也必须遵守父 anchor 与安全检查。

## 4. 产品与网络层注意事项

### 时效性

余额变化、首次 mint、remint、继承和协作变更，对采用正常 gap=2 策略的出块者通常需要
再等待 indexer 提交两个 BTC 高度才进入所选 profile。包括失效变化：在新状态已出现、
旧历史高度仍被合法引用的窗口内，旧 pass 仍可能用于出块。这是已有历史 selector 语义，
不能表述成“最新失效立即禁止所有旧高度出块”。

gap 不丢弃这两个区间的能量记录，也不改能量公式；但更晚使用新的能量、协作和资产状态
可能改变期间的挖矿结果或奖励，不能承诺收益完全不变。不能将 10→12 的相对变化当作
“没有时效成本”，也不能把两个 BTC 高度承诺为固定等待分钟数。

若紧急升级要求某类存量 pass 立即停止后续权益，应另行明确跨 BTC/USDB activation 的
共识规则；不能依赖建议 gap 或最新状态的 UI 判断来达成全网撤销。

### 经济激励及验证边界

按当前 [UIP-0003](./UIP-0003-pass-energy-formula.md)，在余额不变、pass 持续 Active
且没有中间事件的固定公式区间，未触及能量上限时的增量为
`floor(owner_balance_sats / 100000) * delta_height`。评审中引用的
`balance * 10000 * delta_height` 是开发期已废止公式，不用于本次收益估算。

这类平稳区间内，更高 `H` 可能更早跨过 level 阈值；首次 mint 也可能更早获得资格。
当前 UIP-0005 每级把难度系数降低 100 bps，作用于基础难度，并有最低系数和整数取整限制；
不能一律解释为相对当前实际难度再降低 1%。另一方面，减仓惩罚、继承折损、协作退出、
pass 休眠或失效都可能使更新状态更不利，较旧的合法历史状态可能暂时保留更多能量或资格。
UIP-0011 还使用同一历史状态的矿工 BTC 资产 aggregate；不能只用 level 推断最终收益。

因此，测试目标是测量不同 gap 下的封块机会、规范链收益及传播等待成本，不预设
“gap=0 一定占优”或“必须证明 gap=0 没有系统性优势”。按矿工记录结果，并在相同 BTC
事件、余额、初始等级、算力及网络条件下交换 gap 配置进行对照，覆盖平稳增长、跨 level
阈值、首次资格和能量下降等场景。

固定封块延迟的 fakepow 能检查 selector、执行、奖励账本及恢复是否正确，但其封块速度
不随真实难度变化，不能证明真实算力竞争中的收益公平。收益分析另用明确假设的随机模型
或受控真实 PoW，报告样本量、波动范围和限制；公网观察独立记录。发现明显策略优势时
重新评估默认值与风险说明，不能自动把本地配置升级为共识限制。

### 不同 gap 共存

0、1、2 等配置可以共存，不因 gap 不同拒绝 peer 或区块。合法生产者把规范链 anchor 推到
更高位置后，后继矿工不能选择低于父 anchor 的高度；当本机 `L-2<P` 时，不能立即恢复
目标 gap=2。但 anchor 的绝对高度不倒退，不妨碍实际 gap 随本地已提交高度 `L` 前进而恢复。

例如 gap=0 矿工先在 `L=100` 时把规范链 anchor 推到 100，随后由 gap=2 矿工接续。
假定历史起点不限制选高、状态与资格均有效、同高复用未耗尽，且没有其他块提前推进 anchor：

| 后继矿工的最新完整高度 `L` | 父 anchor `P` | 所选高度 `H` | 实际 gap `L-H` |
| --- | --- | --- | --- |
| 100 | 100 | 100 | 0 |
| 101 | 100 | 100 | 1 |
| 102 | 100 | 100 | 2 |
| 103 | 100 | 101 | 2 |

恢复依赖 BTC 状态继续提交；只连续产出 USDB 块而 `L` 不前进，不会积累 gap。复用耗尽时
仍按第 2 节推进或等待。gap=0 矿工若穿插出块，并再次把规范链 anchor 推到更高位置，会
重新压缩后继矿工的余量；足够频繁时可能长期无法恢复到 2。仅出块而未推进 anchor 不会
重置这个过程，且不同节点的 `L` 不同，不能把某个矿工的实际 gap 当成全网统一值。

在其他条件相同时，引用较新状态可能使更多尚未同步的节点暂缓验证，延迟区块导入和在
该分支上继续出块，并可能增加其在分支竞争中失去规范链位置与奖励的风险。这是暂时不可
验证的传播风险，不是仅因 gap=0 就被判为无效；状态补齐后仍按既有重试路径验证与导入。
风险大小取决于同步、传播和竞争情况，不能保证 gap=0 一定承担足以抵消其潜在收益的成本。

默认值一致有利于效果稳定，可将其理解为非强制的性能协作约定。它不是已证明的激励相容
机制；偏离建议仍可产生合法区块，共识安全不依赖矿工共同遵守 gap=2，也不能要求 validator
通过本地 tip 强制维持余量。

当其他节点的索引差距超过 2，或某节点 RPC 故障时，仍需暂缓验证并自动恢复。这个策略
不承诺所有矿工同时选中同一高度，也不解决故意从历史高度缓慢推进的问题；已有 age 上限
只限制精确 anchor 的连续复用次数。

暂缓验证还可能影响依赖该块的后继块，不能假定只有最先使用新高度的矿工承担等待成本。
`算力份额 * w / 600` 至多是短窗口、稳定出块等简化假设下的粗略估计，不能作为一般的
孤块概率或收益损失公式。实际 gap 小本身也不等于故障，应结合真实等待和恢复指标判断。

### BTC 长间隔与 anchor age 上限

gap 可以留下尚未引用、但本机已有完整状态的更高高度。BTC 暂停前进时，参考策略可在
age 耗尽后按 `P+1` 逐步使用这些状态，故 public `M` 的标定需要考虑实际剩余高度。

假定 `F<=P<=L`、本地最新高度 `L` 不再变化、从 `P` 到 `L` 的状态均可用且有合法 candidate、chain
checkpoint 不变化，并满足当前父 age `0<=A<=M`，可继续组装的 USDB 子块数上界为：

```text
remaining_blocks = (M - A) + (L - P) * (M + 1)
```

当前 anchor 剩余 `M-A` 次复用，每推进一个 BTC 高度允许首次 age=0 和其后 `M` 次复用。
该上界按逐级使用高度计算；如果选高策略直接跳到更高的 `L-G`，不会用满中间高度的余量。
实际 gap=2 且 `A=0` 时为 `3M+2`，可粗略称为约 `3M`；缺少可用状态、资格变化或其他
阻断会使可持续出块数减少。它不是固定等待时间，也不是协议保证的最大陈旧窗口：gap
可以配置，父 anchor 也可能已推进。不能用默认 2 推导全网强制的 freshness 上界。

development `M=6650` 不能替代 public 参数标定。Nightly 应使用小 `M` 验证完整的
“耗尽 → 让步 → 再耗尽 → 等待 → 新状态恢复”，并覆盖实际 gap 已被其他矿工压缩的情形。

### 恢复与工作刷新

- 深重组 halt、失败发布、数据库恢复等保护不因历史 gap 放宽；不自动寻找“安全旧高度”。
- anchor 不倒退约束比较的是同一分支的父子块。USDB 正常换到另一条合法分支时，应基于
  新父块重算，不能拿被丢弃分支的最大 anchor 当作全局不可回退水位。
- 当前 `HasSystemStateChanged` 比较 current ID 与上次成功组块 ID。加入 gap 后必须分开
  保存“成功组块时观察的最新 head”和“实际选择的历史 state”，否则 current 永远不同于
  selected，可能每轮轮询都取消重建工作。
- 失败不得提前确认刷新基线；parent 改变、age 到达边界、配置变化和新 head 到来都应重算。
  只看到新 head 但还没成功完成历史查询时，不能吞掉后续重试。

## 5. 配置、展示与升级

建议实现名：geth `--miner.usdb-anchor-gap`，`miner.USDBConfig.AnchorGap`；node-kit
`USDB_MINER_ANCHOR_GAP`。均为拟定名称，当前尚不可执行。Go 默认配置与 node-kit 默认值
一致为 2，显式 0 必须保留；不要用“值为零就取默认”的写法。
首版只提供静态配置，不增加在线自适应调参；拒绝负数、非整数和超出高度类型范围的值。

设置放在本机运行配置，不放进共识 `network.json`、activation registry 或数据兼容性身份。
升级只需更新相应软件与运行配置并重启受影响服务，不隔离旧库、不重置矿工资格授权。
节点工具须能区分配置值、容器实际参数和未知状态，避免升级后以为 gap=2 而仍运行旧参数。

状态至少区分：

- 最新完整高度 `L`、当前工作选择的 `H`、configured/actual gap。
- 选高原因：正常 gap、历史起点、父 anchor、age 上限导致推进。
- 所选 pass、anchor age/max age；等待时指出目标高度、可用高度和具体失败原因。

目前 `usdb_mining.py` 按最新 readiness context 查询 candidate。工具接入时须区分
“最新状态资格”和“实际所选高度资格”，否则首次 mint 会显示可挖但 builder 等待，或
remint 后 UI 显示新证而当前工作仍使用旧证。实际工作以 Go builder 的结构化诊断为准；
诊断不存在时显示未知，不复制一套会漂移的选高算法。优先扩展现有本机 mining 诊断路径，
无需新增持久化监控服务；矿工授权、reorg guard 及 SourceDAO 前提继续独立保留。

### 首次资格与等待提示

若候选从 BTC 高度 `h_mint` 起有效，正常保留 gap 时需要 indexer 提交到
`X = h_mint + G`。工具应显示“按当前 gap，预计 indexer 提交到 BTC 高度 X 后可用于组块”，
并展示当前 `L`。这不是预计发现 PoW 区块的时间，也不是保证高度 X 时必然具备资格。
前提包括候选持续有效、历史查询安全以及矿工授权等既有条件；父 anchor 或 age 让步可能
让它更早进入工作。加法越界、诊断不足或候选生效高度未知时，不输出推测的 X。
继承、remint 和协作变化的提示同样区分最新可见状态与工作正在使用的历史状态。

### 观测定义与告警边界

记录以下事件时，按同一网络/rules scope、BTC 高度、snapshot/system identity 匹配，
不能仅按高度比较重组前后的不同状态。下列名称描述拟采集语义，不表示已发布的 RPC 字段。

| 观测 | 定义与用途 |
| --- | --- |
| `state_ready_at` | 本节点首次观测到该精确历史状态完整可查询的时间；附采样周期和误差 |
| `block_received_at` | 首次收到引用该状态的 USDB 块的本地时间；按区块 hash 去重 |
| `state_lead_seconds` | `block_received_at - state_ready_at`；正值表示收到块前已有状态，负值表示状态随后才可用 |
| 等待及导入事件 | 等待原因、入队/重试/退出时间、导入完成或拒绝/淘汰结果；区分外部状态等待和父块等待 |
| 矿工工作诊断 | 组块时的 `L/H`、配置 gap、实际 `L-H`、age、所选 pass 和让步原因 |

单节点时长使用单调时钟；跨节点对照同时记录可校准的时间与误差。在观测启动前已经可用
的状态，应标记首次可用时间未知，不能把本次进程启动或补查时间冒充 `state_ready_at`。
尚未恢复的样本保留为未完成，不能从等待时长统计中丢弃或按零计入。
另行记录 RPC 故障或恢复屏障造成的可用性中断；曾经查询成功不表示该身份此后始终可用。

要估计节点 `i` 的同步差距，需多个节点观测同一身份，计算
`w_i = ready_at_i - min(ready_at_观测组)`，明确最快的是观测组节点而非全网最快节点。
记录校时误差、采样间隔和观察窗口；单机的 `state_lead_seconds` 或入队时长不能直接
反推出这个 `w_i`。BTC/USDB header timestamp 也不能代替节点状态可用时间。

validator 从收到的 selector 只知道 `H`，不知道生产者组块时的 `L`；不能用验证者自己的
`L-H` 冒充生产者实际 gap。实际 gap 来自对应矿工的工作诊断，缺失时保持未知。

按场景统计等待比例、等待/导入时长分位数、最长等待、未恢复样本、队列淘汰及规范分支
结果。保留有界的事件证据，聚合指标不把每个高度/hash 作为无限增长的标签。
实际 gap=0 或状态提前量短不单独触发异常；持续等待、队列积压/淘汰、错误身份、恢复
屏障或无法取得安全状态，仍沿用并补充对应告警，不能通过延长告警时间掩盖停滞。

## 6. 实施顺序与验收

实现按 A → B → C 推进，D 单独记录收益分析及测试网观察；所有 gap 实现及下述验收尚待执行。
既有无 gap 的功能矩阵通过，不代表下面的新增场景已验收。

### A. Go 选高与完整组块

在 `internal/usdb/client.go` 接入现有历史 state-ref RPC，拆出纯选高函数，修改
`builder.go` 和 worker 的刷新记录；沿用 anchor transition 与 profile resolver。
配置接入 `miner.USDBConfig`、CLI/TOML 默认及显式零值解析。无需修改 validator 接受规则。

测试覆盖：0/1/2、起点、无父 selector、父高度更高、本地尚未追到父高度、age 的 M-1/M
边界、counter/height 溢出、checkpoint 更换上限、同高度身份变化与未知 policy。
完整 builder 测试必须使用 `L` 与 `H` 不同的 profile/ID/版本，证明奖励与难度使用所选
历史数据；补 candidate 不存在不搜索其它高度、查询期间恢复、失败重试及刷新不空转。
activation 前后、USDB 分支切换、历史 registry revision 兼容与冲突都要覆盖。

### B. node-kit 配置和运维语义

接入 compose/启动参数、配置查看与运行态核验、升级保留显式 gap、矿工诊断与 status 展示。
补上首次 mint/remint 的等待提示；确认普通 CatchingUp 不被再次变成 mining 全局阻断。
验证无需重新授权或数据重建，且 gap=0 与新默认 2 均能明确落到实际 geth 参数。

本轮文档同步澄清 UIP-0007 的历史选高和 validator 边界；实际 builder、工具及 RPC 使用
说明仍按本节落地。Handbook 在命令可用后说明默认值、覆盖方式、时效取舍和等待提示，
不提前把拟定参数写成已发布功能。默认值与具体让步算法只在本文定义，避免与 UIP-0007 重复维护。

### C. 独立多节点实测

扩展已有 3 节点/2 矿工矩阵，继续使用独立 Core/BH/indexer 和真实查询：

| 场景 | 必须观察的结果 |
| --- | --- |
| 相同网络推进、gap=0/1/2 对照 | 控制验证者落后 1/2 个高度；证据解释引用高度是否可用，记录等待而非只比较最终 head |
| gap=2，验证者落后 3 个高度 | 仍进入等待；上游恢复后无人工重连或 chain 重启自动导入 |
| 秒级延迟与连续 BTC 块 | 注入 10/30/60/120 秒等可用时间差及短间隔/批量提交，区分高度 gap 与时间缓冲，核对观测事件 |
| 多矿工混合 0/1/2 | 高 anchor 先入链后其余矿工跟随；随 L 前进验证实际 gap 从 0→1→2 恢复及再次被压缩，绝不回退 anchor 或因 gap 不同拒绝块 |
| 小 M、BTC 停止前进及实际 gap 被压缩 | 连续验证逐级让步及可用高度耗尽；没有新高度时停止组块，新状态恢复后自动继续 |
| 首次 mint/remint/继承/协作/失效边界 | 按所选 H 切换 pass 与经济视图，UI 不把最新资格冒充实际工作状态 |
| BTC 与 USDB activation 边界 | 历史 BTC 规则和子块 chain policy 分别正确，不混用公式、registry 或身份 |
| BH/indexer 故障、恢复、竞争分支 | 仍遵守已有安全屏障，恢复后规范历史、两名矿工收益与状态一致 |
| 观测重启、重组、父块等待和未恢复样本 | 未知时间不伪装成零，按身份区分分支；后继块等待可见，不遗漏长期未完成样本 |

对照分别从隔离的同等初始条件启动，并显式记录实际 anchor；不能让 gap=0 先推进了父
anchor，再把被迫跟随的 gap=2 样本当作正常 gap 对照。记录状态等待次数/时长、导入时间、
实际 gap、竞争分支和恢复证据，不将真实网络噪声或 fakepow 算力差异归因于 gap。

Fast 放纯策略、历史组块及观测投影回归；Nightly 放有界延迟对照及小 M 的连续让步；
Weekly 执行混合 gap、秒级延迟/连续块、多轮故障与经济状态边界。按可复现输入和已知
事件验证每层输出，不将一次随机运行的等待率当作概率表的验收门限。

### D. 收益分析与测试网观察

与功能矩阵分开报告：fakepow 验证账本和协议行为；受控真实 PoW 或明确假设的随机模型
研究难度和出块竞争；测试网观察验证真实节点的同步时间分布。各项均须保留来源、配置、
样本和适用范围，不能互相替代。

收益对照覆盖同等余额/等级/算力、跨等级阈值、首次资格及余额/协作下降；交换矿工的 gap
配置，按规范链有效奖励、封块尝试/时间和竞争分支损失归一化比较，避免仅比较某次运行
的账户余额。加入多种算力份额、网络延迟及 BTC 事件序列，报告不确定性；如发现策略
优势，明确原因和量级，不通过调整测试断言隐藏差异。

测试网至少记录观测节点集合、gap 与实际运行参数、上游/网络条件、采样误差和观察时段，
区分稳态与启动追块。先保留默认 2，根据测量结果评估是否需要后续调整默认值；运行者
仍可显式覆盖，无需重置网络。public `M` 标定另行遵循 UIP-0007 的共识参数流程。

# 冷钱包持币与地址轮换

[矿工证介绍](README.md) · [首次铸造](mint.md) · [继承与协作](manage.md) · [控制台核验](../services/control-plane.md#minerpass-v2-草案与入金前核验)

本页适用于明确启用 **MinerPass V2** 的网络，测试网版本见[网络资料](../networks/testnet.md)。目标是在持有 BTC 和有效矿工证期间，减少持币地址的公钥暴露；**私钥始终留在自己的钱包中**，不交给节点、控制台或代铸服务。

## 先理解冷地址的含义

这里的“冷地址”是使用独立密钥、尚未公开公钥的接收地址，不等于“余额为零”，也不等于“使用硬件钱包”。推荐选择钱包明确标识的**原生 P2WPKH** 地址：接收时输出中记录公钥哈希，花费时会公开公钥。Bitcoin 主网的 `bc1q` 前缀还包括其他脚本类型，不能只凭前缀判断钱包是否支持后续继承。参见 [BIP-141](https://github.com/bitcoin/bips/blob/master/bip-0141.mediawiki#p2wpkh)。

Taproot（主网通常为 `bc1p`）输出本身包含输出公钥，换一个从未花费的 Taproot 地址也不满足隐藏公钥的目标。commit 的中间地址可以是 Taproot，最终接收地址不必是 Taproot。参见 [BIP-341](https://github.com/bitcoin/bips/blob/master/bip-0341.mediawiki#script-validation-rules)。

不要把同一把已公开公钥的密钥换一种地址格式当作新冷地址。向服务导出公钥、可推导该地址公钥的扩展公钥，或签署会公开公钥的证明，也会破坏这个目标；入金前核验只需手工填写接收地址，无须由接收地址签名。此方案没有更换 Bitcoin 签名算法，不能称为完整的抗量子保证。

## 选择操作路径

下表中的 D 是**实际铭文 sat 对应的 commit 输入来源地址**，E 是 reveal 直接接收铭文的地址；钱包名称、交易浏览器的 From 或支付服务费的地址不能代替 D。

| 目标 | 操作条件 | 对冷地址的影响 |
| --- | --- | --- |
| 首次开户 | E 符合开户条件，`prev` 为空；可由另一地址出资 | E 只接收，不需要花费或签名 |
| 换地址并继承 | D 持有全部 `prev`；E 符合开户条件；D 参与合规 commit 花费 | D 的公钥会暴露，新 E 仍可只接收 |
| 保留原地址修改 | D=E，来源检查通过；保留旧证能量时填写 `prev` | 原地址要花费，不再具有未暴露公钥的属性 |

开户条件是 **reveal 交易执行前精确余额为 0 sat，且在目标 USDB 规则作用域内从未持有有效 pass**。这是“零余额开户”，不是向零地址或销毁地址转账。协议并不要求该地址在整个 Bitcoin 历史中从未使用；为了隐藏公钥，操作上应选全新密钥和地址。

同一块中先到账的普通转账也计入余额，1 sat 就会使余额条件不成立；reveal 自己随铭文交付的 BTC 不计入它的交易前余额。有效证后来休眠、被继承、转走或销毁，都不会清除原地址的有效持有历史。余额查询失败、历史缺失不能当作零余额。

## 首次开户：先铸造，再入金

1. 在自己保管密钥的钱包中生成全新接收地址 E，确认地址类型及备份。暂不向 E 转账，也不要用小额“测试入金”提前激活地址。
2. 用另一个已备有手续费的地址 D 准备铸造。确认钱包支持原样 JSON、指定 reveal 接收地址，以及接收和保护 E 上的铭文；同一钱包不同地址也要明确区分。
3. 按[首次铸造](mint.md)生成 `v: 2` 的标准证，或按[协作模板](manage.md#准备协作铭文)生成协作证；首次开户不填写 `prev`。在控制台分别填写 D、E 并保存预期收益地址或 Leader 配置。
4. 外部钱包完成 commit/reveal，直接交付到 E，保存真实 inscription ID。E 无须签名；代铸平台先收再转给 E 属于转让，不是本流程的直接开户。
5. 等待规范链确认及 USDB 稳定索引覆盖，按下节完成指定铭文核验。全部匹配后，再向 E 转入计划持有的 BTC，继续检查入金确认和能量变化。

第三方仍可以向空地址预先铸造或小额转账。若核验发现收到的不是预期铭文、配置不符或地址已被占用，停止入金，优先换一个全新地址重来。不能因钱包里出现了一张名为 USDB 的铭文就转入余额。

## 入金前核验什么

优先使用控制台的[“核验后再入金”](../services/control-plane.md#minerpass-v2-草案与入金前核验)，逐项核对：

| 项目 | 通过条件 |
| --- | --- |
| 目标网络 | 选定 USDB 网络、规则版本和 Bitcoin 数据源正确；testnet-v1 仍使用真实 BTC 主网 |
| 指定铭文 | 完整 inscription ID 正确；reveal 已达到要求的确认深度，索引处理到相应高度 |
| 状态与归属 | 该张证为 V2 `active`，铸造接收者和当前持有者均为 E |
| 实际来源 | 链上重建的 sat 来源与预期 D 一致，来源签名形式受核验工具支持；不是仅比较钱包标签 |
| 完整内容 | 类型、`usdb_main` 或 Leader 字段、`prev` 全部与保存的草案一致 |
| 继承结果 | 每张列出的旧证均已 `consumed`；首次开户没有 `prev` |

首次开户在协议层允许第三方出资，但入金核验仍检查来源。协议有效不等于“是我预期的那次铸造”；缺少历史区块或输入证据时，应恢复依赖再核验。工具当前支持 P2PKH/P2WPKH 的 SIGHASH_ALL，以及 P2TR key-path 的 DEFAULT/ALL 来源。

没有自己的控制台时，请目标网络提供具备同等核验能力的服务；仅靠 Bitcoin 浏览器的 From、收到铭文或 `mining check` 的 READY，无法完成上述核验。核验结果是当时规范链上的观测，过期、网络变化或重组后应重新核验，不能长期复用一次成功提示。

## 修改或继承：从 D 轮换到 E

现在 D 指旧持币和持证地址，E 是下一次使用的全新地址。修改收益地址、变更协作对象、从协作证改为标准证，都可采用相同流程。

1. 查清 D 当前持有的旧证 ID、状态和自身能量。`prev` 只可引用当前属于 D 的 Active / Dormant 证；不能同时合并其他地址的证。
2. 生成全新 E，保持未入金。在新铭文中填写新的收益／Leader 配置和非空 `prev`。
3. 让 D 参与 commit，确保实际铭文 sat 来自 D，reveal 直接交付到 E。钱包应选择 D 的普通可花费 UTXO，并保护旧铭文 UTXO；继承不要求把旧证花进 commit。只有代铸平台或其他地址出资，不能代替 D 的来源证明。
4. 按上节核验 E 的新证及全部 `prev` 消费结果。继承成功后旧证已经不能继续使用，不会等到余额迁移后才失效。
5. 核验通过后及时将 D 的持币余额转入 E。检查找零、手续费、未确认交易和残余铭文 UTXO；新旧铭文都要由能识别它们的钱包逐笔管理，不能盲目全选花费。D 不再作为未暴露公钥的冷地址使用。
6. 重新核对矿工所选的新 pass 和收益地址，按[CPU 挖矿](../node/mining.md)更新目标；协作证还要核对 Leader 是否仍有效。

钱包是否能接收 P2WPKH 铭文，和是否能在下次继承时控制 D 的选币，是两个能力。只有一个铭文 UTXO、没有普通 UTXO 可供 commit 时，不要为了付款直接花掉待继承的旧证；先安排来源 UTXO 并确认钱包能够保护旧证。不支持这些操作的钱包，不能仅凭“支持铭文”就视为可完成轮换。

每张 `prev` 的结算后自身能量按 95% 保留并向下取整；commit 花费、余额下降和操作顺序还可能导致额外扣减，不能承诺总共只损失 5%。未列入 `prev` 的 D 上旧证不会自动迁移。Leader 跨地址后，固定 pass 绑定和跟随旧地址的协作者都不会自动指向 E，需要各自重新绑定，详见[管理说明](manage.md)。

## 暴露窗口和操作边界

D 的花费交易一旦公开，其中的公钥就可能被观察到；并非等 commit 确认才开始暴露。之后还要等待 reveal、确认、索引和核验，再迁移余额。因此窗口不能保证只有几个区块。testnet-v1 的稳定状态落后 BTC 链尖 10 个区块，具体等待见[稳定高度说明](mint.md#usdb-的稳定高度已覆盖铸造高度)。本流程不支持在 commit 中同时向 E 转入持币余额来消除等待窗口。

V2 的最低承诺是防止持有人未参与相关花费时，第三方仅凭强制赠予替换其已有证、消费其旧证，或借用其已有 BTC 余额建立攻击者的绑定。它不阻止空地址抢占，也没有独立的铭文内容签名授权。

持证地址应专用于持币和明确的 pass 操作。向未知地址普通付款，特别是向攻击者准备的 commit 地址付款，可能被用于构造看似来源合法的 pass 操作；错误铸造或被诱导付款不在上述保证内。公钥是否曾经公开也不是索引器的开户判定条件，需要钱包持有人自行管理。

精确资格规则见 [UIP-0016](../../UIP/UIP-0016-miner-pass-operation-eligibility.md)。

# 转让、换地址与协作

[矿工证介绍](README.md) · [首次铸造](mint.md) · [CPU 挖矿](../node/mining.md)

这些操作会改变当前矿工资格或能量。操作前先查清旧证的 `pass_id`、持有地址、状态及自身能量；节点显示的挖矿有效能量不一定等于可继承的自身能量。

## 持有和转让

使用钱包的**铭文转移**功能发送矿工证，并在签名前核对具体 inscription ID 和接收地址。普通 BTC 转账不等于转移指定铭文；管理余额时也应使用能识别并保护铭文的钱包功能，避免误花费携带矿工证的输出。

一张活跃证转给另一个 Bitcoin 地址后会变成 `dormant`，停止增长能量，也不再具备独立挖矿资格。即使两个地址属于同一个钱包，这条规则仍适用。转回原地址也不会自动恢复 `active`。

接收方若想保留旧证的可继承能量，需要在接收地址上**新铸造一张证，并用 `prev` 引用旧证**。转让不会自动改写原铭文的 USDB 收益地址，新证需要填写接收方自己的收益地址。

只转移铭文并不要求把该地址的全部 BTC 一起转走。转出过程中如果原持有地址的余额单位下降，会先结算相应的能量扣减，再冻结旧证；不要把转让前看到的能量视作接收方必然能继承的数值。

## 重新铸造并继承旧证

适用于保留能量的换收益地址、接收转让后的重新启用，或标准证与协作证之间切换。每次都会创建一个新的 `pass_id`，旧铭文内容保持原样。

### 操作前核对

- 所有要继承的旧证，当前必须由**新证的 Bitcoin 接收地址**持有；只属于同一钱包、同一 USDB 收益地址还不够。
- 旧证可以是该地址当前的活跃证，也可以是其持有的 `dormant` 证。引用当前活跃证时，不需要先转出去把它变成 `dormant`。
- 不能继承 `invalid`、`consumed` 或 `burned` 证；列表中每个完整 ID 只写一次。
- 若先进行了转让，先等转让被稳定状态和索引确认，再开始继承，便于核对所有权。

### 生成新铭文

下面是继承一张旧证、铸造新标准证的模板。将**两个占位符**都替换为真实值：

```json
{
  "p": "usdb",
  "op": "mint",
  "v": 1,
  "usdb_main": "YOUR_USDB_REWARD_ADDRESS",
  "prev": ["YOUR_OLD_PASS_ID"]
}
```

`usdb_main` 可以保持原收益地址，也可以填写你准备使用的新地址。`YOUR_OLD_PASS_ID` 替换为要继承的旧证完整 inscription ID，包括 `i` 和序号。首次使用建议只继承一张，核对清楚后再进行多证合并。

按[钱包铸造步骤](mint.md#3-在钱包中铸造)提交，并确保**新证接收到持有旧证的同一个 Bitcoin 地址**。需要合并多张时，把各自的完整 ID 放入 `prev` 数组；其中任何一张不满足条件，整次新铸造都无效，不会只继承符合条件的部分。

### 成功后的结果

等待[稳定高度与索引确认](mint.md#确认矿工证生效)，核对新证 `active`、被继承旧证 `consumed`，以及新证的收益地址或 Leader 绑定。

当前 v1 每张旧证的自身能量按 **95% 保留并向下取整**，再合计成为新证的初始能量。例如，某旧证在继承时结算后的自身能量为 `1000`，新证从它继承 `950`。如果交易引起旧持有地址余额单位减少，还可能先发生余额能量扣减；因此不能简单把操作前查询值乘以 95% 当成最终结果。

旧证被消费后不能再次继承，也不能通过转账恢复。若没有填写 `prev`，新证从零能量开始，原活跃证变为 `dormant`，其能量不会自动带入新证。

更换了 USDB 收益地址后，矿工节点仍需按 [CPU 挖矿](../node/mining.md)对新地址执行 `mining check`，通过后执行 `mining enable` 应用新目标。该操作不会转移旧收益地址中已经收到的 USDB。

## 协作矿工证

协作证让自己积累的能量按协议规则贡献给 Leader。你仍持有自己的 Bitcoin 铭文和 BTC，**无需把它们转到 Leader 地址**。但是协作证不能作为自己独立挖矿的身份；挖矿身份和收益接收使用 Leader 标准证的 `usdb_main`。

矿工证协议不自动定义协作者分润，也不因为填写绑定就自动给你的地址付款。参与前应与 Leader 明确收益分配方式和退出安排。

### 选择绑定方式

| 方式 | 填写字段 | 行为与取舍 |
| --- | --- | --- |
| 固定绑定某张标准证 | `leader_pass_id` | 铸造时目标必须已是有效的活跃标准证；Leader 后续换证，绑定不会跟随，需要自己重新铸造调整 |
| 跟随某个 Bitcoin 持有地址 | `leader_btc_addr` | 跟随该地址当前的活跃标准证；Leader 在原地址换证后自动跟随，也会接受新证的收益地址变化 |

地址跟随填写的是 **Leader 持有标准证的 Bitcoin 主网地址**，不是其 USDB 收益地址，也不是你的接收地址。该地址暂时没有活跃标准证时，可以存在协作绑定，但当前不贡献有效能量。

### 准备协作铭文

以下两种模板**只选一种**，并替换其中的占位符。固定证绑定：

```json
{
  "p": "usdb",
  "op": "mint",
  "v": 1,
  "leader_pass_id": "LEADER_ACTIVE_STANDARD_PASS_ID"
}
```

地址跟随绑定：

```json
{
  "p": "usdb",
  "op": "mint",
  "v": 1,
  "leader_btc_addr": "LEADER_BITCOIN_MAINNET_ADDRESS"
}
```

协作模板不填 `usdb_main`，也不填旧字段 `usdb_collab`；两个 Leader 字段不能同时出现。按[钱包铸造步骤](mint.md#3-在钱包中铸造)操作，**接收地址仍是你自己的 Bitcoin 地址**。

已有标准证或协作证需要保留能量时，在选定模板里加入 `prev`，并满足上面的[继承条件](#重新铸造并继承旧证)。同一持有地址铸造协作证也会替换原活跃标准证，原证不能继续独立挖矿。

生效后，通过支持矿工证查询的服务核对自己的证为 `active/collab`、绑定字段正确，并且当前 Leader 能解析为活跃标准证。`mining check --address` 是独立矿工预检入口，不能用来证明某一张协作证已经贡献能量。

### 更换 Leader 或退出协作

通过新铸造声明新的选择：换 Leader 时铸造新的协作证；准备自己挖矿时铸造标准证并填写自己的 `usdb_main`。需要保留自身能量时用 `prev` 继承旧协作证，并接受相同的 5% 继承折损。

新证只继承自己旧证的自身能量，不继承 Leader 汇总的能量。更换节点配置不能改写已经上链的协作绑定。

## 常见问题

| 现象 | 处理 |
| --- | --- |
| 转到自己的另一个地址后不能挖矿 | 这是所有权变化，旧证变为 `dormant`；在新持有地址重新铸造并用 `prev` 继承 |
| 换了钱包显示的收款地址，但旧证归属没变 | 以铭文实际持有位置为准；生成新地址不会自动转移旧铭文 |
| 继承失败 | 核对每个 `prev` 的完整 ID、当前持有地址和状态，确认没有重复、已消费或已销毁的证；先查清原因再重铸 |
| 铸造新证后旧证失效 | 同一地址只有一个活跃名额；核对新证是否符合原本目标，不能通过删除钱包记录撤回链上操作 |
| 协作证活跃，但没有贡献 | 核对 Leader 是否仍为活跃标准证、绑定方式以及自身能量；固定绑定不会跟随 Leader 换证 |
| 想编辑旧证的收益地址或绑定 | 已上链内容不可改；用新铸造表达新选择，需要继承时填写 `prev` |

日常只是停止 CPU 挖矿时，使用 [`usdb-node mining disable`](../node/mining.md#停止挖矿)，无需转让、销毁或重新铸造矿工证。停止本机挖矿不会注销矿工证；证仍为 `active` 时，其自身能量继续按 Bitcoin 侧的余额和区块计算。
